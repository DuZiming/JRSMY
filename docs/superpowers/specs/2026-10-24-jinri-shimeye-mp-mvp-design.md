# 今日食咩野 · 小程序 MVP 设计文档

- **日期**：2026-10-24
- **状态**：设计已确认，待实施
- **阶段**：MVP（验证阶段，个人主体小程序）
- **原始需求**：[今日食咩野.txt](../../../今日食咩野.txt)

## 1. 背景与目标

解决「今天吃什么」的决策疲劳：年轻人不知道吃啥、家庭主厨不知道配什么菜单买什么菜。核心痛点：

1. 录入菜品门槛高（要填名称/图片/材料/热量/辣度等一大堆）→ **AI 拍照识别自动填**是本产品的核心差异化
2. 每天选菜费脑子 → 按需求**随机生成整单**或**大转盘逐类转**
3. 确认菜单后不知道买什么 → **买菜清单**（可勾选已买）

**验证期成功标准**：录入不劝退（AI 识别预填后基本只需确认）、用户每天愿意打开它做决定、菜品库随时间变厚。

## 2. 范围

### 2.1 MVP 范围（单用户闭环）

- 厨房：每人默认一个（隐式，不建 kitchens 集合），不做邀请/多厨房
- 菜品管理：增删改查、多级标签（来源 / 类型 / 健康标签）、拍照/上传图片（≤9 张，压缩后上传）、**AI 识别预填表单**
- 今日菜单：随机整单推荐（左滑换一批）、大转盘逐类选菜、按需求生成（人数/荤素搭配/忌口）、买菜清单（勾选已买）、按天隔断的历史记录
- 用户：头像昵称、默认偏好（忌口/人数/搭配）

### 2.2 明确不做（延后，见 §10 预留清单）

| 功能 | 延后原因 |
|---|---|
| 美食广场（UGC 社区） | 个人主体类目审核过不了社交类目，待企业主体后二期 |
| 大白菜（充值/消耗/转账） | 虚拟支付链路，验证期不做 |
| 多厨房、邀请协作 | 依赖单用户闭环先跑通 |

## 3. 技术选型（已确认：方案一）

**原生微信小程序 + 微信云开发（wx.cloud）**，零自建后端：

| 层 | 选择 | 说明 |
|---|---|---|
| 前端 | 原生 WXML/WXSS/JS | 无跨端框架，最快验证 |
| 数据库 | 云开发 NoSQL 文档数据库 | 菜品=弹性文档结构，天然匹配 |
| 文件 | 云存储 | 菜品图片，`sizeType: compressed` 压缩后上传 |
| 后端 | 云函数 ×1（`recognizeDish`） | 仅 AI 识别走云函数，其余全部客户端直连数据库 |
| 登录 | 天然免登录 | OPENID 自动可用，**不做任何登录页/登录流程** |

成本：验证期 ≈ 0（成长计划免费 token + 基础套餐）。

## 4. 数据模型

3 个集合，全部使用「**仅创建者可读写**」权限预设（MVP 单用户成立；云函数以管理员权限运行不受限，**无需自定义安全规则**）。

### 4.1 `dishes` 菜品

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | string | 菜品名（必填） |
| `photos` | string[] | 云存储 fileID 数组，至少 1 张 |
| `source` | enum | `home` 自做 / `dineout` 外吃 / `takeout` 外卖 |
| `type` | enum | `meat` 荤 / `veg` 素 / `staple` 主食 / `soup` 汤 / `drink` 饮品 |
| `tags` | string[] | 健康标签：低脂轻食、香辣馋嘴、清淡健康…（可自定义） |
| `ingredients` | `[{name, amount}]` | 材料（AI 识别填充，amount 可空） |
| `calories` | number | 热量 kcal（可空） |
| `spicy_level` | number | 辣度 0-3（可空） |
| `practice` | string | 做法备注（可空） |
| `ai_meta` | object | `{ model, at }` 识别来源标记（可空） |
| `kitchen_id` | string | **预留二期**，MVP 固定填 `k_<openid>` |
| `is_public` | boolean | **预留二期**美食广场，默认 false |
| `created_at` / `updated_at` | Date | |

### 4.2 `menus` 今日菜单

| 字段 | 类型 | 说明 |
|---|---|---|
| `date` | string | `YYYY-MM-DD`，历史按天隔断的分组键 |
| `items` | `[{dish_id, name, photo, type, calories}]` | **菜品快照**而非纯引用——菜品日后被删/改，历史菜单不烂 |
| `requirements` | object | 生成需求快照：`{people, composition 如 {meat:1, veg:1, staple:1}, avoid: []}` |
| `mode` | enum | `random` 随机整单 / `wheel` 大转盘 |
| `total_calories` | number | 确认时算好 |
| `shopping_list` | `[{name, amount, bought}]` | 确认菜单时从各菜 `ingredients` 聚合（同名材料合并数量），勾选改 `bought` |
| `creator_openid` | string | **预留二期**多人厨房，MVP 恒等于本人 |
| `created_at` | Date | |

### 4.3 `users` 用户

| 字段 | 类型 | 说明 |
|---|---|---|
| `nickname` / `avatar` | string | 用官方「头像昵称填写能力」（`button open-type="chooseAvatar"` + `input type="nickname"`），不用已废弃的 `getUserProfile` |
| `settings` | object | 默认偏好：常驻忌口 `avoid`、默认人数 `people`、默认搭配 `composition`，生成时自动带出 |
| `ai_usage` | object | `{date, count}` 每日 AI 识别次数（限流用） |
| `cabbage` | number | **预留二期**大白菜，MVP 恒为 0，无任何消耗/充值逻辑 |
| `created_at` | Date | |

索引：`dishes._openid`（内置）；`menus` 按 `_openid` + `date` 倒序建组合索引。

## 5. 页面与交互

纯文字自定义 tabBar（`tabBar.custom = true`，不配图标，规避图标资产与预留位问题）：

| Tab | 页面 | 职责 |
|---|---|---|
| 今日菜单 | `pages/menu/menu` | 今日菜单卡片 + 「生成菜单」入口 + 历史记录（按天隔断，新在前） |
| | `pages/menu/create` | 生成流程（见 §5.1） |
| | `pages/menu/detail` | 菜品列表、热量合计、买菜清单（勾选已买） |
| 菜品库 | `pages/dishes/dishes` | 列表/卡片视图切换、分类筛选（默认全部：来源/类型/标签） |
| | `pages/dishes/edit` | 新增/编辑共用：拍照或选图（≤9 张）→ 上传 → AI 识别预填 → 人工修正保存 |
| | `pages/dishes/detail` | 大图、信息、材料、编辑/删除（删除需确认弹窗） |
| 我的 | `pages/profile/profile` | 头像昵称、默认偏好、大白菜（预留显示）、关于 |

### 5.1 菜单生成流程

1. **设需求**：人数、搭配（荤 N / 素 N / 主食 N / 汤 N，可 0）、忌口/排除标签（从健康标签和辣度里选）；带出 `users.settings` 默认值
2. **选模式**：
   - **随机整单**：一次生成完整菜单，不满意**左滑换一批**
   - **大转盘**：按搭配逐类转——先转荤菜，确定 → 转素菜 → … 直到配齐；每类转出的结果可「重转」
3. **确认** → 生成菜单详情：快照落库、聚合买菜清单、算热量合计

### 5.2 推荐算法（客户端纯函数，放 `utils/`）

- 按需求过滤池：`type` 匹配 + 排除 `avoid` 标签/辣度
- **避免重复**：优先排除近 7 天已进过菜单的菜（由最近 menus 反查）；池不够时自动放宽到全部
- 池空处理：该类型跳过并提示（「还没有荤菜，先去加菜或改搭配」），不卡死
- 随机整单 = 每类各随机取 N 个；转盘 = 单类随机取 1 个

## 6. AI 识别链路（云函数 `recognizeDish`）

```
客户端                                云函数 recognizeDish
──────                                ──────────────────
chooseMedia 拍照/选图(≤9张, compressed)
  → uploadFile 逐张上传云存储
  → callFunction({ fileID: 封面图 })
                                      ① getWXContext().OPENID → 限流检查
                                         （users.ai_usage，20 次/人/天）
                                      ② downloadFile 取同环境图片 → base64（内网，免费）
                                      ③ 调多模态模型（@cloudbase/node-sdk 的 ai 能力，
                                         wx-server-sdk 无 AI 能力）
                                      ④ Prompt 要求只回 JSON：名称/类型/来源猜测/标签/
                                         材料[{name,amount}]/热量估计/辣度
                                      ⑤ 解析容错：剥 markdown 代码围栏 → JSON.parse 失败
                                         重试 1 次 → 字段级校验（type 等枚举不符则丢弃该字段）
  ← 结构化字段
预填表单 → 用户修正 → 保存（AI 只预填，不自动保存）
```

**模型选择**——实现时按 AI 技能跑**两步预检**（先计费资格、后模型组就绪，顺序固定，不凭记忆猜 API）：

1. 优先「小程序成长计划」免费 token 内的视觉模型（运行时 `DescribeAIModels` 查实际可用视觉 SKU；成长计划 token 覆盖云函数内调用）
2. 不可用则启用 `cloudbase` 组多模态模型（如 GLM-5V-Turbo，需 Token Credits 资源包，验证期花费可控）

**降级**：识别失败/超时/限流 → toast 提示，表单保持手填。AI 是增强，永远不是阻塞路径。

## 7. 异常处理

| 场景 | 处理 |
|---|---|
| 空菜品库 / 类型池空 | 生成入口预检 + 分类提示；转盘跳过该类继续 |
| 菜品被删 | 菜单历史存快照，不受影响 |
| 图片上传失败 | 自动重试 1 次，失败提示但不阻塞表单其他字段 |
| AI 失败/限流 | 见 §6 降级 |
| 云函数/网络异常 | 统一 toast + 可重试 |

## 8. 测试策略

- **Jest 单测**（逻辑抽 `utils/` 纯函数）：推荐组合（搭配约束/池空/近 7 天去重放宽）、买菜清单聚合（同名合并）、热量合计、AI JSON 解析容错
- **云函数**：本地模拟 + 真环境真实菜品照片联调
- **页面走查**（DevTools 模拟器）三条核心路径：
  1. 加菜（AI 识别）→ 菜品库可见
  2. 设需求 → 随机/转盘 → 确认菜单
  3. 买菜清单勾选、历史按天查看

## 9. 前置条件与工具链

- 腾讯云账号**实名认证**（未实名创建环境会失败且报错不明显）
- 开发者工具里点「云开发」开通环境，登录选「**微信公众平台登录**」；**不要**勾「使用云服务」（会自动新建腾讯云账号，是「环境看不到」的头号成因）
- 项目结构：`miniprogram/`（源码）+ `cloudfunctions/`（云函数）
- 微信开发者工具 **Nightly** 版 + `wechatide` CLI（自动化编译/预览）；AI 能力要求基础库 **3.7.1+**
- 本地需 Node.js 环境（Jest、云函数依赖安装）
